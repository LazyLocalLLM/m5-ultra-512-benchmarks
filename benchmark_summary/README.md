# Benchmark summary

By Local LLM L-Plate. Follow [@LazyLocalLLM on X](https://x.com/LazyLocalLLM) for new benchmarks.

ELI5: One page with the best speed I have measured for each model on one Mac Studio M5 Ultra 512 GB. Every line links to the finding folder that holds the report and the raw rows.

Updated 28 Nov 2026 00:44 SGT. Max, median and code are decode speed in tok/s for one user, how fast the reply is written. Prefill is prompt-reading speed in tok/s.

## Three decode speeds per model

ELI5: People measure speed in different ways, so I show three. The max is the top speed with everything tuned for it. The median is closer to what you get in daily use. Code is the model writing code the way it would for you, with its own sampler.

- **Max.** Greedy decoding at temperature 0 on a real task, with the engine's drafting tuned for speed. The model writes a new code module from the code in the prompt. The prompt is code where code wrote faster, and the line says so.
- **Median.** The model's own recommended sampler, on a prompt of mixed prose and code.
- **Code.** The model's own recommended sampler while it writes a new code module from the code in the prompt, the same task as Max. It is the setup closest to a coding agent. A blank cell has not been measured yet.
- Each figure is the middle value of its timed runs. The run count, prompt length, reply length and date are on each line.
- Reply length is part of the setup and differs by line. Longer replies wrote faster where I measured both, so compare two Max lines only at the same reply length. The full table below has each model at every reply length I ran.
- **Prefill.** How fast the engine read a cold prompt. It is the prompt's tokens divided by the time to the first token, as the middle value of every timed request on one engine release at one prompt size and one kind of text, over all of its runs. I show the best line of the engine of the best max, on a current release. The line names the prompt size and the text, because reading speed changes with both. Another engine is shown only where it read more than 5% faster on the same text at the same size, since two runs of one setup differ by about that much. `prefill.csv` in this folder has every engine's line at every size, with its run ids.
- "not run yet" means I have not measured it. It does not mean the engine cannot do it.
- I rerun each model when its engine ships a new stable release. A line marked "older release" in the full table has been replaced by a newer run and no longer competes for the best line, even where its figure is higher.

## Check it yourself

ELI5: Each figure here is recomputed from the raw rows in its finding folder. You can do the same.

- `summary.csv` in this folder holds every decode line above with its run id. The picture and video cells link to the finding folders that hold their rows.
- From the top of the repository, `python3 tools/summarize.py findings/FOLDER` prints the median and range of each run in that folder.
- `prefill.csv` holds each model's prefill line on every engine, text and prompt size I ran, with its run ids. The `shown` column marks the line in the table above.
- Each model name in the tables links to its weights. The same names are in the `weights` column of `summary.csv`. The row with a draft head joined here links to the base weights, and finding 9 has the join steps.
- If I have set an engine up wrong, [open an issue](https://github.com/LazyLocalLLM/m5-ultra-512-benchmarks/issues). I will rerun it and post the fix.
